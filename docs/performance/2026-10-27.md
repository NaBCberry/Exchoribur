# 2026-10-27 性能评估与优化

本轮覆盖编辑、时间轴绘制与取样、视频画面复制、音频设置、设备连接和后台发送。
时间线范围修复已先独立提交为 `992c370`。性能改动按核心、时间轴、媒体和设备分别提交。

## 环境与测量范围

- Windows 10.0.26200，24 个逻辑处理器，.NET 10.0.14，Release 构建。
- 固定 `DOTNET_TieredCompilation=0`，同一基准先预热，测量 7 轮，取每轮平均耗时的中位数。
  `SlowestRoundMicroseconds` 是最慢一轮的平均值，不是单次操作的 P95。
- 分配量取当前测量线程；设备后台线程、原生解码器与显存不包含在该分配量内。
- 基线对应时间线修复完成后的代码；实际素材只读取，不写回，不将工程或媒体收进仓库。
- 实际工程：1 个块、5887 帧，灯光结束时间约 8810.044 秒。
  视频缓存大小 3,635,834,097 字节，时长 9110.656 秒。
- `ffprobe` 确认视频为 HEVC、1920×1080、50 fps；音频为 AAC、48 kHz、双声道。
  文件名中的“1080P60”不能作为实际帧率依据。
- 另用生成的 1 万/10 万块、10 万帧单块、1080p/4K 连续像素缓冲和模拟设备扩大负载。

原始结果：[baseline.json](baseline.json)、[optimized.json](optimized.json)。
绝对耗时受系统调度、频率与内存状态影响，不能将微基准比例直接当作整机交互加速比例。

## 结果

| 场景 | 优化前 | 优化后 | 解释 |
| --- | ---: | ---: | --- |
| 实际工程 5887 帧块移动 | 190.451 µs / 259704 B | 0.026 µs / 96 B | 不再复制、排序整段帧内容 |
| 10 万帧块移动 | 3898.697 µs / 约 4.40 MB | 0.028 µs / 96 B | 耗时不再随块内帧数增长 |
| 1 万块单块替换并重建快照 | 1.365 ms | 0.845 ms | 少量修改与原有块顺序合并，避免全表重排 |
| 10 万块单块替换并重建快照 | 14.285 ms / 17.09 MB | 7.892 ms / 13.48 MB | 仍需复制不可变快照、验证 ID 与分组 |
| 1 万块随机时间取样 | 40.817 µs | 0.354 µs | 跳过已结束的前缀，遇到尚未开始的块即停止 |
| 10 万块随机时间取样 | 437.099 µs | 0.636 µs | 对稀疏、按时间排列的大工程收益明显 |
| 1080p 画面复制到位图 | 1.073 ms | 0.894 ms | 连续行布局整帧复制 |
| 4K 画面复制到位图 | 6.685 ms | 4.580 ms | 约减少 31% 复制耗时，包含解码器接口到托管缓冲再到位图 |
| 101 次音量变化的输出设备设置次数 | 101 | 1 | 音量仍每次更新；设备 ID 或播放器变化才重设输出 |
| 界面不消费通知时，200 次发送积累的通知 | 202 | 1 | 快照继续更新，界面只保留一次待处理通知 |

绘制重叠遮罩另做同次运行的参考对照：保留原逐对检查算法，1 万个不重叠块的重叠计算
为 7.374 ms、247600 B；有序扫描及缓存分组为 0.01072 ms、24 B。
该项只计算重叠范围，不包含文字、色段绘制、窗口合成和 GPU。
随机乱序、嵌套和同起点块的测试核对了全部遮罩范围及重复次数，保持原有重叠显示语义。

实际工程只有一个块，原取样已经很便宜：0.098 µs → 0.169 µs，分配 216 B → 184 B。
该微小场景没有取样耗时收益；不能据大工程结果声称所有工程的取样都加速。
时长现按不可变快照缓存，不再在每个播放节拍中遍历全部块。

## 视频与音频

实际视频经生产使用的 libvlc 解码器预热 2 秒，再测量 8 秒；音频保持解码并设为静音。
前后均约 50 fps，与源文件的 50 fps 一致，帧回调间隔 P95 约 21 ms。
4 个输出设备可以枚举；本轮没有证据显示实际素材的解码吞吐不足。

这项测的是解码回调，不是完整窗口的呈现帧率，也未测声卡到扬声器的延迟、听感或
两小时以上持续播放。首帧时间和 CPU 占用在不同轮之间波动，不将其变化算作优化收益。
控制台测试过程中 libvlc 仍输出窗口置顶及退出阶段 HEVC 缓冲错误日志；
这些日志保留为后续桌面运行复核项，本轮未改动原生解码与停机逻辑。

画面复制保留有行填充时的逐行路径；连续行与带填充的行均有像素内容回归测试。
不降分辨率、不更改采样率或播放速度。内存中的完整画面复制仍然存在，
4K 场景的复制成本仍需计入界面每帧预算。

音频优化位于播放器适配器，保持音量变化和真实输出切换生效。
播放器替换时即使设备 ID 相同也重新设置；缓存使用弱引用，避免预览清空后继续保留大帧缓冲。

## 下位机连接与通信

未提供实际下位机连接参数，本轮使用模拟通道，没有向外部设备发包。
连接耗时结果只用于确认后台流程可运行，不代表串口、Wi-Fi 或固件响应延迟。

- 发送请求提交约 0.08 µs/次、40 B/次，实际写入由后台任务独占执行。
- 相同载荷去重约 0.04 µs/次、48 B/次，当前不是主要 CPU 热点，未为此更改协议。
- 保留原“一个正在写入的帧 + 最新一个待发送帧”规则；界面通知现在也会合并，避免另一路积压。
- 回归覆盖阻塞写入时提交立即返回、仅保留最新帧、连接过程中断开、写入失败、
  断开与释放期间等待已开始的写入、丢弃过期请求，以及释放后忽略排队通知。
- 未更改 AUTH/STREAM 字节、UDP 重复次数/间隔、串口稳定等待或写入超时。

后续真实硬件评测应记录连接耗时、请求到出线/设备生效的延迟、丢包、
持续收发与断线重连；这些结果不能由模拟通道推断。

## 成本与后续重点

大型时间轴首次取样时建立前缀结束时间索引，约额外 8 字节/块；
少于等于 16 块时直接扫描。编辑快照不提前建立该索引。
早期超长块跨越大量后续短块时仍可能扫描较长候选范围，当前未承诺所有布局均为对数耗时。

大量真实重叠仍需绘制对应的遮罩对；此轮去掉的是不可能相交的块对检查。
完整交互延迟仍受色段绘制、文本、窗口合成和不可变快照分配影响。
下一轮应在桌面窗口对高分辨率播放与连续编辑同时采样，再决定是否继续改造画面传输或快照结构。

```powershell
./scripts/measure-performance.ps1 -OutputPath artifacts/performance/report.json

  -ProjectPath '工程.exb' `
  -MediaPath '参考视频.mp4' `
  -OutputPath artifacts/performance/report.json
```

已还原依赖时可加 `-NoRestore`。脚本使用 `dotnet <程序集>.dll`，
不再启动曾出现 `0xc0000142` 的独立基准启动器。
输出文件缺省放在忽略提交的 `artifacts/`；实际工程与媒体路径仅作输入，不写入结果 JSON。

验证包含 Release 构建、完整测试、代码风格检查与 `git diff --check`。
本机验证不替代 macOS/Linux 的窗口渲染与真实媒体/设备验收。
